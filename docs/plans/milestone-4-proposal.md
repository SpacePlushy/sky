## Goal

present the project to someone who has five minutes.

### Done when

- Visible passes can raise a browser notification a chosen number of minutes before they start,

- The README opens with what the project is, a screenshot, how it is verified, and how to run it.

## Decisions

| # | Decision | Choice | Main alternative |

## Alerts

- **Browser notifications.** A bell control asks for permission only when clicked. The lead time
  is 5, 10, or 15 minutes, stored in the browser. The page schedules a notification for each
  upcoming visible pass from the pass list and the server clock, reschedules when the passes
  refresh, and never notifies twice for one pass. They work only while a dashboard tab is open,
  and the control says so.
- **Calendar export.** `GET /api/satellites/{id}/passes.ics?days=7&visibleOnly=true` returns one
  event per visible part: start and end in UTC, a summary such as "ISS visible, up to 36°", a
  description with rise, peak, and set directions, and a display alarm 10 minutes before. Event
  UIDs come from the satellite and the pass's rise time, so importing a later file updates events
  instead of duplicating them. Lines are folded at 75 octets and end in CRLF, as RFC 5545 requires.

## End-to-end tests

Against the demo data at the fixed clock, where the first passes are known from the Skyfield
reference:

- The page loads, shows the offline and simulated-clock notice, and the telemetry values match
  `/api/satellites/25544/now` at the same instant.
- The pass table lists the same passes as `/api/.../passes`, with the visible ones marked in text.
- Selecting a pass draws it on the sky plot and keeps the selection when the list refreshes.
- Times show in America/Phoenix whatever the browser's own zone: the test runs the browser in
  another zone.
- At 375 px wide nothing scrolls sideways, and the pass list is readable.
- Turning on notifications asks for permission, and a pass inside the lead time produces exactly
  one notification (the browser's clock is driven by Playwright).
- The calendar link downloads a file that parses, with one event per visible part.
- No request leaves the machine: the test fails on any request to a host other than the API.

## Build order

1. Calendar export in the API, with tests (RFC 5545 structure, UTC times, stable UIDs, folding).
2. Notifications in the dashboard, with unit tests for scheduling.
3. Playwright setup, the end-to-end tests, and a CI job.
4. Screenshots and the README.
5. Docs: verification record, handoff guide.

## Out of scope

- Notifications when no dashboard tab is open (web push needs keys and a service).
- Accounts, hosting beyond the local machine, and brightness predictions.
